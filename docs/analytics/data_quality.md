## 1. Активные пользователи — исправлено

Было: `COUNT(DISTINCT COALESCE(member_id::text, user_id))` считал и «осиротевшие» строки
`screen_time`, у которых `user_id` уже нет в `members` (Антон, Ваня, Олеся). Отсюда 12 > 11.

Стало: `JOIN members m ON m.id = st.member_id` → **9** активных (11 всего участников).
Проверка сходится: `active_members_yesterday = 9`, `daily.active_members = 9`.

Остаток: строки-сироты физически остались в `screen_time` (5 рядов). На метрику теперь не
влияют, но влияют на `syncs` — см. п. 5. Рекомендую разово почистить:
`DELETE FROM screen_time WHERE member_id IS NULL OR member_id NOT IN (SELECT id FROM members);`
(или оставить как исторический след — тогда учитывать в подписях).

## 2. `daily.tasks_done` — исправлено

Причина: `WHERE done_at >= %s AND done_at <= %s`, где `%s` — `date` (`2026-11-07`).
PostgreSQL приводит дату к `2026-11-07 00:00:00`, поэтому задача от 07.11 14:10
отсекалась. Стало `done_at < %s::date + 1` — задача попала в выгрузку: **1**.
То же исправление применено к `achievements.earned_date`.
Проверено: `daily` за 07.11 → `tasks_done = 1`, `summary.tasks_done_yesterday = 1`.

## 3. История — 1 день (ожидаемо)

`screen_time` появилась только 07.11.2026, поэтому `daily&days=N` возвращает одну строку.
График активности и любые тренды начнут наполняться автоматически; в дашборде стоит
подпись «данные с 07.11.2026» (уже добавлена). Параметр `days` принимается (1–365),
но данных за более ранние даты нет. Retention/когорты по этому экспорту в принципе
не считаются: он отдаёт только суточные агрегаты, без привязки к пользователю.

## 4. `top_apps` и «минуты» — не выводим на дашборд

Факты из выгрузки за 07.11: `com.google.android.googlequicksearchbox` — 893 мин,
`com.GoodTools.Uninstaller` — 889 мин, `com.miui.cleaner` — 889 мин, `Android` — 163 мин.
Это сумма по всем участникам за день (экспорт складывает `top_apps[].minutes` из всех
строк `screen_time`), но значения накопленные: у одного устройства
`total_seconds = 577 228` за сутки ≈ **160 часов**, что физически невозможно.
Источник — клиент (`SyncService.kt` / `MainActivity.getUsageStats`): интервалы
`MOVE_TO_FOREGROUND → MOVE_TO_BACKGROUND` считаются без сброса (в т.ч. экран выключен,
процесс убит, перекрытия событий), поэтому копятся «лишние» часы.
**Решение для дашборда:** лист «Приложения» сохраняется как технический, но на «Дашборд»
не выводится; в блоке «Качество данных» стоит пометка «скрыт до фикса клиента».
Так честнее: цифры не выглядят как продуктовый инсайт. После фикса клиента достаточно
включить блок обратно (он уже описан в спецификации).

## 5. Осталось: `syncs` считает строки-сироты (новое)

- `active_members_yesterday` = `JOIN members` → **9**;
- `daily.syncs` = `COUNT(*) … JOIN members` → **9**;
- `nightly` `syncs_yesterday` = `SELECT COUNT(*) FROM screen_time WHERE date = %s` → **12**
  (`server.py`, блок «synced_yday», ~строка 3428 — JOIN не добавлен);
- `features` «Синхронизация экранного времени: вчера» = 12 (тот же `synced_yday`).

То есть на дашборде в блоке функций «синхронизаций» больше, чем активных пользователей.
Рекомендация: либо добавить тот же `JOIN members`, либо считать `syncs = COUNT(DISTINCT member_id)`.
Плюс `active_families_yesterday` (~строка 3402) тоже не джойнится с `members` — теоретически
может посчитать семью, оставшуюся только в сиротских строках. Тот же JOIN закроет вопрос.

## 6. Прочие особенности экспорта (важно для интерпретации)

- **`format=json` игнорирует `table`** — отдаёт один комбинированный JSON (удобно для отладки,
  но нельзя просить JSON по одной таблице). Неизвестный `table` CSV-режима молча отдаёт `summary`.
- **`syncs` — не «число синков», а число строк `screen_time`** (уникальность `user_id+date`),
  т.е. метрика почти дублирует «активных пользователей» и чувствительна к сиротам.
- **`total_accounts` (6) ≠ `total_members` (11)**: `accounts` — это `users` (аккаунты сервера,
  `email_verified`), `members` — участники семьи. В дашборде подписаны раздельно.
- **`features` смешивает продукт и привлечение**: строки «Новые семьи/участники/аккаунты»
  — это не функции. В дашборде функции отфильтрованы от acquision-событий (хелпер `D:E`).
- **Топ достижений ограничен 20 строками**, сейчас пусто (`achievements` = 0) — ожидаемо.
- **Один endpoint = один день «вчера»**, сервер считает по UTC. Дата данных всегда
  отображается на дашборде, чтобы не путать с «сегодня».
- **HTTP, не HTTPS**, секрет в query-строке. Для Google-импорта это ок, но в логах прокси
  секрет виден; храним только в Script Properties / скрытом листе.

## Что я бы чинил в первую очередь (продуктово)

1. `syncs`/`active_families`: добавить `JOIN members` — 10 минут, убирает противоречивые цифры.
2. Разово почистить `screen_time` от строк без `member_id` (или добавить в те же JOIN везде).
3. Клиентский учёт screen time: не суммировать интервалы без закрытия (фоновые/выключенный
   экран, перекрытия), поставить суточный кап/нормализацию — иначе `top_apps` и `total_seconds`
   дискредитируют всю аналитику.
